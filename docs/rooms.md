# Rooms

A room is the only place anything social happens in genzh. Communities own
channels, strangers meet in moments, and two people talk in a DM — all three are
rows in `rooms`, and telling them apart is the single most load-bearing
distinction in the product.

## 1. The three kinds of room

| Kind                    | `community_id` | `category`      | Expires    | In discovery | Reaped when empty |
| ----------------------- | -------------- | --------------- | ---------- | ------------ | ----------------- |
| **Community channel**   | set            | anything        | no         | no           | no                |
| **Direct conversation** | `NULL`         | `'dm'`          | no         | no           | no                |
| **Playground room**     | `NULL`         | anything else   | **always** | **yes**      | **yes**           |

One predicate decides it, in `crates/domain/src/room.rs`:

```rust
/// Is this one of the throwaway rooms on the playground side of the app?
pub fn is_playground(&self) -> bool {
    self.community_id.is_none() && !self.is_direct()
}
```

It is asked as a question about the room rather than stored as a flag, because
the two facts that decide it are already columns and a third one could disagree
with them.

**A DM is not a playground room.** It is standalone like a moment, so every rule
written as "standalone rooms are throwaway" would take it — and a direct
conversation that vanished because nobody replied for three minutes, or that
appeared in a stranger's feed, would be a serious bug. `DIRECT_CATEGORY` (`"dm"`)
is spelled once in the domain and every rule keys off it.

## 2. Room types and the three pillars

Twenty `room_type` values in three families. `RoomFamily` is **derived** from
`room_type` in Rust (`RoomType::family()`), not stored.

### 💬 Conversation

| Type    | Label          | Media |
| ------- | -------------- | ----- |
| `text`  | Chat           |       |
| `voice` | Voice & screen | ✓     |
| `video` | Video grid     | ✓     |
| `stage` | Stage          | ✓     |

### 🎮 Social Games

| Type               | Label            | Media |
| ------------------ | ---------------- | ----- |
| `truth_or_dare`    | Truth / Dare     |       |
| `would_you_rather` | Would You Rather |       |
| `hot_takes`        | Hot Takes        |       |
| `poll`             | Live poll        |       |
| `trivia`           | Trivia quiz      |       |
| `debate`           | Debate arena     |       |
| `guess_who`        | Guess Who        |       |
| `game`             | Party games      |       |
| `activity`         | Activity lounge  | ✓     |

### 🧭 Social Discovery

| Type              | Label             |
| ----------------- | ----------------- |
| `random_chat`     | Random chat       |
| `anonymous_chat`  | Anonymous chat    |
| `match_interest`  | Match by interest |
| `friend_finder`   | Friend finder     |
| `topic_room`      | Topic rooms       |
| `confession`      | Confessions       |
| `quick_chat`      | Speed chat        |

`confession` and `quick_chat` predate the pillars and are kept as aliases of
`anonymous_chat` and `random_chat`; nothing new should use them.

**Media rooms** are `voice`, `video`, `stage` and `activity` — plus any DM,
because calling somebody is not a different room from messaging them.
`Room::require_media()` is the single gate, and a media join on anything else is
`UNSUPPORTED_ROOM_TYPE` (400) before any token is minted.

**`room_type` is not updatable.** Turning a text room into a voice room
mid-flight would strand clients and invalidate every media token already issued
for it.

Client-side, `roomTypes.ts` (one in `apps/web/src/lib/`, one in
`apps/mobile/src/lib/`) carries the label, icon and family for each type, and
`isExperienceRoom()` decides whether a room opens as a live experience screen or
as a transcript.

## 3. The record

`crates/domain/src/room.rs`, table `rooms`.

| Column                 | Notes                                                            |
| ---------------------- | ---------------------------------------------------------------- |
| `id`                   | UUID, generated by the application                               |
| `community_id`         | `NULL` for standalone rooms — half of `is_playground()`          |
| `owner_id`             | who started it; the feed shows them as the host                   |
| `name`                 | 1–64 characters (`ROOM_NAME_MAX_LEN`)                             |
| `topic`                | the line under the name                                           |
| `category`             | `gaming`, `debate`, `music`, … or `dm` — the other half           |
| `room_type`            | enum, see above                                                   |
| `visibility`           | `public` \| `unlisted` \| `friends_only` \| `private`             |
| `status`               | `created` \| `waiting` \| `active` \| `ending` \| `ended`         |
| `is_anonymous`         | replaces profiles with room-scoped personas                       |
| `position`             | sort order inside a community                                     |
| `max_participants`     | media rooms only; `NULL` means `MEDIA_ROOM_MAX_PARTICIPANTS` (50) |
| `current_participants` | maintained by `recount_participants`                              |
| `started_at`           | when the session began                                            |
| `expires_at`           | the deadline; **always set on a playground room**                 |
| `emptied_at`           | stamped when the last person leaves, cleared when anybody joins    |
| `ended_at`             | set by expiry or by the reaper                                     |
| `family`               | see [Known gaps](architecture.md#9-known-gaps) — written, never read |

> `visibility` gates **discoverability**, not access. Discovery queries filter on
> `visibility = 'public'`; access is decided by the `view_room` permission
> through `RoomAccess::require_visible()`. `friends_only` is defined in the enum
> and is **not enforced anywhere** — treat it as unimplemented.

## 4. Lifecycle

```
   POST /rooms
        │
        ▼
   ┌──────────────────┐   last one leaves: emptied_at = now()   ┌───────────────┐
   │ active, occupied │ ─────────────────────────────────────▶  │ active, empty │
   │                  │ ◀─────────────────────────────────────  │               │
   └────────┬─────────┘   somebody joins: emptied_at = NULL     └───────┬───────┘
            │                                                          │
            │                       ── playground rooms only ──         │
            │ expires_at <= now()                    empty past the grace period
            │ rooms.expire_ephemeral · 30s           rooms.reap_empty_playground · 60s
            │                                                          │
            └──────────────────────────┬───────────────────────────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │ ended — status='ended', ended_at set  │
                    │ (expiry also clears participant rows) │
                    └──────────────────────────────────────┘
```

Expiry can take an occupied room too: the deadline does not care who is still
in it. Only the reaper needs the room to be empty.

A community channel and a DM never leave the top row. Neither arrow down can
reach them — the reaper filters them out, and neither is ever given an
`expires_at`.

### Creation

`RoomService::create` is the single path — community channels, playground rooms
and DMs all come through it.

```rust
let is_playground = community_id.is_none() && category != DIRECT_CATEGORY;
let duration_minutes = if is_playground {
    Some(input.duration_minutes
        .unwrap_or(DEFAULT_PLAYGROUND_TTL_MINUTES)   // 360 = 6h
        .clamp(1, MAX_PLAYGROUND_TTL_MINUTES))        // 1440 = 24h
} else {
    input.duration_minutes    // normally None
};
```

A moment nobody gave an end to still ends. A community channel expires only if
its creator explicitly asked for it, which nothing in the UI does. A DM never.

### The two ways a playground room dies

**1 — its deadline.** `rooms.expire_ephemeral` (every 30s) ends everything with
`expires_at <= now()`. Because every playground room has a TTL, this is also
what eventually clears a room abandoned without a clean exit — a closed laptop
lid, a killed process.

**2 — everybody leaving.** `rooms.reap_empty_playground` (every 60s) ends rooms
whose `emptied_at` is older than `PLAYGROUND_EMPTY_GRACE_SECONDS` (180s):

```sql
UPDATE rooms
   SET status = 'ended', ended_at = COALESCE(ended_at, now())
 WHERE status = 'active'
   AND community_id IS NULL
   AND category <> 'dm'
   AND current_participants = 0
   AND emptied_at IS NOT NULL
   AND emptied_at <= now() - make_interval(secs => $1)
```

`emptied_at` is stamped by `recount_participants` the moment the last person
leaves and cleared the moment anybody joins, so the reaper reads a settled fact
rather than racing the count. The grace period exists because an empty room is
the normal state between the last person leaving and the next arriving — ending
one the instant its count hits zero would close a call out from under somebody
who is still reconnecting.

Both are tunable: `CRON_EPHEMERAL_ROOM_EXPIRE_SECONDS`,
`CRON_PLAYGROUND_REAP_SECONDS`, `CRON_PLAYGROUND_EMPTY_GRACE_SECONDS`.

### What the reaper deliberately does not do

It never touches `room_participants`. `RoomRepository::prune_stale_participants`
exists and is **intentionally left uncalled** — a standing decision. Stale
participant rows are handled by the TTL instead, which is part of why every
playground room now has one. Do not wire that method into `jobs::register`
without asking first.

Note also that `prune_stale_participants` has had its room-ending behaviour
removed on purpose (`rooms_ended: 0`), so that community channels keep their
history. The reaper above is the only thing that ends a room for being empty,
and it is scoped to the playground.

## 5. Discovery and the feed

### The scope, and why it is a filter

Five surfaces show rooms to somebody who is not in them. **Every one carries the
same scope**, in SQL:

```sql
WHERE visibility = 'public'::room_visibility
  AND status     = 'active'::room_status
  AND community_id IS NULL
  AND category <> 'dm'
  AND (expires_at IS NULL OR expires_at > now())
```

| Surface           | Endpoint                             | Query                            |
| ----------------- | ------------------------------------ | -------------------------------- |
| The swipe feed    | `GET /rooms/feed`                    | `list_feed`                      |
| The browse wall   | `GET /rooms/discovery`               | `list_discovery`                 |
| Trending          | `GET /rooms/trending`                | `list_trending`                  |
| Live now          | `GET /rooms/live`                    | `list_live`                      |
| One-click random  | `GET /rooms/random`                  | `find_random`                    |
| Ranked "for you"  | `GET /recommendations/rooms`         | `crates/recommend/src/rooms.rs`  |

This is a **filter, not a ranking**. A community channel scored low would still
surface for anybody who scrolled far enough, and a stranger dropped into
`#general` has walked into a place they do not belong. A weight can be retuned to
zero by accident; a `WHERE` clause cannot.

The recommender additionally excludes rooms the viewer is already in and rooms
they own, and since it now only considers standalone rooms it no longer joins
`communities` at all — the quarantine rule it enforced only ever applied to rooms
that had one.

### The feed

`GET /rooms/feed?category=&limit=&offset=` → `PlaygroundFeedResponse`.

```jsonc
{
  "rooms": [
    {
      "id": "…", "name": "Unpopular opinions", "topic": "…",
      "room_type": "hot_takes", "category": "debate",
      "current_participants": 4,
      "expires_at": "2026-08-26T20:27:22Z",
      "host":  { "id": "…", "handle": "…", "display_name": "…", "avatar_url": null },
      "faces": [ /* up to 5 public profiles, oldest joiner first */ ]
    }
  ],
  "next_offset": 20      // absent at the end of the feed
}
```

Ordered for swiping rather than browsing: a room with somebody in it beats an
empty one outright, then busiest, then freshest, with `id` as a stable tiebreak.

**Three queries regardless of page size** — the rooms, their participants, then
one batch lookup of every profile behind both sets of ids
(`AuthService::public_identities`). Resolving a host per card would be a
waterfall the length of the feed.

**`offset`, not a cursor.** The ordering is live — rooms fill up and empty out
between pages — so there is no stable key to page from. The occasional duplicate
is cheap to drop client-side; a cursor into a shifting list would silently skip
rooms instead.

**Anonymous participants are never in `faces`.** A room that hides who is inside
it must not show them on the card outside it.

### What the clients do with it

- **Mobile** — `PlaygroundFeedScreen`: a `FlatList` snapped to a *measured* page
  height (`onLayout`, not `window.height - tabBar`, because Android counts the
  status and navigation bars inconsistently). `pagingEnabled` plus
  `snapToInterval`; `getItemLayout` is exact, which is also what makes
  `scrollToIndex` safe for a card the reader has not reached.
- **Web** — `PlaygroundFeedRoute`: CSS `scroll-snap-type: y mandatory` with
  viewport-tall panels. The browser's own scroller gives keyboard, trackpad,
  touch and the scrollbar for free.

Each card's background is a gradient hued from the **room id**, not the name: a
uuid spreads evenly over the wheel where short names clump, and the room looks
the same to everybody and after a rename.

> On mobile the SVG gradient's `id` must include the room id.
> `react-native-svg` resolves `url(#…)` against a shared registry, so twenty
> cards all naming their gradient `"ground"` would every one of them paint with
> whichever mounted first.

## 6. Anonymous identities

A room with `is_anonymous` replaces profiles with a room-scoped persona:
`BlueFox#4821`, an avatar seed and an accent colour, generated deterministically
by FNV-hashing `(room_id, user_id)` — so the same person is the same phantom for
the whole room's life and a different one in the next room.

`PATCH /rooms/{id}/persona` lets a participant switch between their persona and
their real profile where the room allows it.

The anonymity is enforced outward as well as inward: anonymous participants are
excluded from feed `faces`, so a room that hides who is inside it does not leak
them on the card outside.

## 7. Migrations and the enum trap

`migrations/` is applied by sqlx — the API applies them at boot, and the
integration harness applies them before building state. Three rules, all learned
the hard way:

**Never apply one by hand** (`psql -f`). It records no row in
`_sqlx_migrations`, so the next sqlx run tries again and fails — which silently
turns every integration test into a *skip*, reported as "N passed" in 0.00s.

**`CREATE TYPE` is not idempotent.** Postgres has no `IF NOT EXISTS` for it:

```sql
DO $$ BEGIN
    CREATE TYPE foo AS ENUM ('a', 'b');
EXCEPTION WHEN duplicate_object THEN null;
END $$;
```

**A new enum label cannot be used by the migration that adds it.** sqlx runs each
migration in one transaction and Postgres refuses `WHERE col = 'newval'` in the
same transaction as its `ALTER TYPE … ADD VALUE` — *"unsafe use of new value"*.
Migration `0017` added ten `room_type` labels and backfilled with them, which
took the whole API down: it could not boot at all. Compare as text instead:

```sql
UPDATE rooms SET family = 'social_games'
 WHERE room_type::text IN ('truth_or_dare', 'would_you_rather', …);
```

And remember that `sqlx::migrate!()` embeds migrations **at compile time**.
Editing a `.sql` and re-running the existing binary changes nothing — rebuild.
